# 用户画像（Proto-Personas）

> 版本：v1 · 2026-08-18 · 依据：`docs/产品说明书-终版.md` §4.1 四角色
> 性质：**Proto-Persona**——基于角色与产品定位的合理假设，未做访谈验证（用户决定不访谈）；作为交互设计、能力矩阵与文案的参考人，非调研结论。

---

## P1 研发工程师 · 小张（28 岁，后端研发）

- **背景**：业务团队后端研发，负责订单服务；会写代码，不懂运维。
- **技能水平**：熟悉业务代码与部署流程概念；没碰过命令行运维工具/堡垒机，服务器于他 = "别人的机器"。
- **痛点**：服务出问题只能 @运维 等 30 分钟+；自己不敢碰服务器，怕把生产搞坏背锅；深夜发版时运维已下班。
- **JTBD**：当我的服务异常时，我想**自己**快速查状态/查日志/重启自己的服务，以便不求人、不背锅。
- **当前替代方案**：群里喊人 / 打开裸监控页只能看 CPU / 凭感觉猜。
- **使用动机**：快 · 安全 · 不求人。

## P2 专业运维 · 老李（35 岁，SRE）

- **背景**：公司唯一资深运维，管几十台服务器 + 云资源；7×24 被 @。
- **技能水平**：全栈运维能力，命令行/脚本/网络/内核都熟。
- **痛点**：大量"帮我看看/帮我重启"的琐碎请求打断深度工作；高危操作审批流程零散（口头发消息），追溯靠记忆。
- **JTBD**：当处理深度故障时，我想让**琐碎查询与常规操作被平台分流**，以便专注复杂问题；当执行高危操作时，我想有留痕的双人审批，以便出事可追溯。
- **当前替代方案**：VPN + 堡垒机 + 命令行 + 群里口头确认。
- **使用动机**：提效 · 少被打扰 · 留痕免责。

## P3 测试/产品 · 阿敏（27 岁，测试工程师）

- **背景**：负责版本测试；偏产品思维，非技术背景加深中。
- **技能水平**：会用测试工具与看板；服务器于她 = "环境"。
- **痛点**：不知道测试环境此刻是否正常，每次要问研发；环境挂了测试被阻塞却后知后觉。
- **JTBD**：当开始测试前，我想**自己确认环境可用性与服务状态**，以便不阻塞、不尴尬。
- **当前替代方案**：问研发 / 直接跑用例撞墙。
- **使用动机**：快 · 自主 · 不尴尬。

## P4 管理者 · 王总（40 岁，部门负责人）

- **背景**：管理研发与运维团队；非技术背景，看结果。
- **技能水平**：看报表、看趋势；不懂任何运维术语。
- **痛点**：不知道系统整体是否健康，总是出事才知道；资源与成本没有直观视图。
- **JTBD**：当我想了解部门系统的整体状况时，我想**随时看到健康度/资源/成本大盘**，以便及时知情、提前决策。
- **当前替代方案**：让下属整理周报（滞后一周）。
- **使用动机**：掌控感 · 及时知情。
