# 意图分类与数据外传盲区 · 全网调研报告

> 调研日期：2026-08-30 · 背景：Voyage AIOps 助手把意图二元分类为 query（只读，免审批）vs execute（变更，需审批），数据外传类意图"把文件内容发给我"被归入 query 放行。本报告从工业设计、学术方向、竞品、安全标准四个维度调研业界做法。

---

## 一、工业设计方向

### 1.1 Anthropic Claude：爆炸半径控制 + 工具风险分级

**核心设计模式**：安全重心从"审核意图"转向"**限制爆炸半径（blast radius containment）**"——不依赖意图判断的准确性，而是让任何意图下可造成的破坏都有物理上限。

- **[How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude)**：工程博客系统阐述沙箱化、权限模式、网络隔离
- **工具风险分级 + 权限模式**：Claude Code 提供 `default` / `acceptEdits` / `plan` / `bypassPermissions` 四档，危险动作需显式批准。官方文档 [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- **allow/deny 规则**：可按工具/路径配置允许或拒绝，危险工具调用默认弹出确认。文档 [Configure permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- **沙箱化**：Bash 工具默认只读/只写当前工作目录 + 子目录，网络访问默认受限可配 `sandbox.network` 白名单。文档 [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- **Hooks 可编程拦截**：`PreToolUse` / `PostToolUse` 在工具执行前返回 `allow/deny/ask`。文档 [Hooks reference](https://code.claude.com/docs/en/hooks)
- **已知边角（警示）**：PreToolUse 返回 `ask` 会**覆盖** `permissions.deny` 规则（[GitHub issue #39344](https://github.com/anthropics/claude-code/issues/39344)）——多层护栏优先级冲突是真实风险，deny 必须优先于 ask

**对 Voyage 的启示**：护栏不依赖意图判断是否准确，而是依赖运行时边界。**"读文件"本身不危险，"读文件+外发"才危险——应在工具调用层而非意图层区分。**

### 1.2 OpenAI：工具审批默认开启 + 输入/输出护栏 + Lockdown Mode

**核心设计模式**：官方安全指南要求**"保持工具审批开启（keep tool approvals on）"**，敏感/破坏性工具强制人工审批。

- **[Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety)**：建议对工具按风险授权、敏感操作挂审批、最小权限——否定"意图是 query 就免审批"
- **[Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)**：`input_guardrails` / `output_guardrails` 在工具调用前后执行守卫函数，可中断执行
- **[Human-in-the-loop](https://github.com/openai/openai-agents-python/blob/cdde4d65/docs/human_in_the_loop.md)**：敏感工具执行前暂停等人类批准
- **Lockdown Mode**：限制 agent 可用功能，缩小提示注入被利用的窗口。媒体报道：[CSO](https://www.csoonline.com/article/4182650/openais-lockdown-mode-is-trying-to-solve-the-problem-that-it-created.html)、[Medianama](https://www.medianama.com/2026/06/223-openai-lockdown-mode-curb-prompt-injection-data-theft-risks/)
- **[Hardening Atlas against prompt injection](https://openai.com/index/hardening-atlas-against-prompt-injection/)**：展示针对工具滥用/数据盗窃的专项对抗

**对 Voyage 的启示**：审批绑定在**工具的危险性**上，而非意图的 query/execute 属性。即使动作是"读"，只要工具是"外发/网络/下载"，也必须审批。

### 1.3 AWS：Bedrock Guardrails 可插拔防护层 + 策略授权 + HITL

**核心设计模式**：护栏是**独立于模型的可插拔层**，在推理前后做输入/输出过滤；工具授权用 IAM + Cedar 策略即代码。

- **[Bedrock Guardrails 组件](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-components.html)**：Denied topics（否定主题）、Sensitive information filters（PII 阻断或打码——**这就是"数据外传"的内容面闸门**）、内容过滤、提示注入检测
- **[Extend Guardrails to Tool Interactions](https://aws.amazon.com/cn/blogs/security/extend-amazon-bedrock-guardrails-to-tool-interactions-using-the-strands-agents-sdk/)**：护栏可挂到 Agent 与工具交互上
- **[AgentCore 细粒度授权](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/security_iam_id-based-policy-examples.md)**：IAM + Cedar 策略在 gateway 层控制"谁能调用哪个工具"
- **[HITL 确认模式](https://github.com/aws-samples/sample-human-in-the-loop-patterns)**：Bedrock Agents 支持执行前暂停等待人工确认
- **反面案例**：Amazon Q 被投诉默认权限过宽（[repost.aws](https://repost.aws/de/questions/QUy-Hg8aLTTjOOiWP68Kj4XA/)）——"默认最小权限"必须成为出厂默认

**对 Voyage 的启示**："否定主题 + PII 阻断 + 策略授权 + 人工确认"四件套，本质上把"读"进一步拆成"读自己数据（放行）"与"读并外发（阻断/审批）"两层。

### 1.4 Google：Agent Gateway + DLP 网关层独立于意图

**核心设计模式**：数据出站防护在 **agent 与外部世界间的网关层**独立强制，与意图分类解耦。

- **[Vertex AI Safety Overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/learn/safety-overview)**：safety filters、grounding 到企业数据源
- **[Agent Gateway ISV 生态](https://cloud.google.com/blog/products/identity-security/introducing-agent-gateway-isv-ecosystem-for-security-and-governance/)**：第三方安全厂商在网关层提供 DLP/数据分类/合规，拦截 agent 对外流量——**这是"数据出站"作为独立防护层的最直接证据**
- **[Symantec DLP + Google Agent Gateway](https://symantec-carbonblack.westconcomstor.com/apac/en/news/insights/2026/symantec-dlp-google-agent-gateway-agentic-ai-security.html)**：DLP 已接入 agent 网关层
- **[Google ADK Safety](https://raw.githubusercontent.com/google/adk-docs/main/docs/safety/index.md)**：Agent 开发套件的安全框架

**对 Voyage 的启示**：**数据出站必须在网关层独立强制，与意图分类解耦**——这直接回答了"不是修好意图分类，而是加独立 egress 层"。

### 1.5 Microsoft：Purview DLP 直接管 Copilot + 官方 ADR 固化审批原则

**核心设计模式**：企业 DLP 直接下沉到 Copilot/Agent 端点，输入与输出双向检测敏感数据；官方用 ADR 文档固化"哪些工具必须审批"。

- **[Purview DLP for Microsoft 365 Copilot](https://learn.microsoft.com/zh-cn/training/modules/purview-ai-secure-copilot/data-loss-prevention-copilot)**：对 Copilot 提示词/回复中的敏感信息检测、阻断、告警
- **[Purview DLP 保护 Copilot 交互](https://learn.microsoft.com/zh-cn/purview/dlp-microsoft365-copilot-location-learn-about)**：输出侧数据外传的标准闸门
- **[Copilot Control System](https://learn.microsoft.com/sk-sk/microsoft-365/copilot/copilot-control-system/overview)**：企业级治理框架
- **[Azure AI Foundry 护栏](https://learn.microsoft.com/zh-tw/azure/foundry/guardrails/guardrails-overview)**：内容安全、prompt shields、grounding
- **[agent-framework ADR 0006-userapproval](https://github.com/microsoft/agent-framework/blob/main/docs/decisions/0006-userapproval.md)**：用文档固化"哪些工具/动作必须人工审批"的原则
- **盲区实录**：Microsoft Q&A 明确有人提问 **Purview DLP 对 Copilot Computer Use 场景的数据外传是否覆盖**（[链接](https://learn.microsoft.com/en-sg/answers/questions/5915515/clarification-on-purview-dlp-coverage-for-copilot)）——说明**当 agent 有 OS 级能力时，端点 DLP 覆盖存在盲区**，与 Voyage 的盲区同源

**对 Voyage 的启示**：把"数据外传防护"当作**独立于意图的横切层（DLP）**，即使 Copilot 判定某操作为只读查询，输出仍会过 DLP；且官方用 ADR 明确"审批绑定工具而非意图"。

### 1.6 主流 Agent 框架：HITL 中断 + 钩子拦截 + RBAC

**核心设计模式**：框架层普遍在"工具调用边界"插入人工或策略闸门。

- **LangChain/LangGraph**：[Interrupts & HITL](https://mintlify.wiki/langchain-ai/langgraph/guides/interrupts)：graph 执行到敏感节点 `interrupt()` 暂停，等人类批准后 `Command(resume)` 继续
- **CrewAI**：[Guardrails](https://docs.crewai.com/v1.15.1/en/enterprise/features/hallucination-guardrail) 与 [Execution Hooks](https://docs.crewai.com/v1.15.1/en/learn/execution-hooks)
- **Microsoft AutoGen**：`UserProxyAgent` 的 `human_input_mode`（NEVER/TERMINATE/ALWAYS）
- **Agno**：内置细粒度 RBAC（[RBAC 文章](https://www.agno.com/articles/gain-fine-grained-access-control-with-built-in-rbac-for-agents-teams-and-workflows)）
- **社区工具**：`@maksiph14/toolwall`（[npm](https://www.npmjs.com/package/@maksiph14/toolwall)）、MCP Security Gateway（[github](https://raw.githubusercontent.com/arjeetanand/mcp-security-gateway/refs/heads/main/README.md)）都在"客户端与工具之间"插一层拦截/审批/审计网关

**对 Voyage 的启示**：框架层共识是——**审批点放在"工具调用边界"，而不是"意图判定之后"**；任何工具（含读类）都可以被 hooks/RBAC 单独设置权限档。

### ▶ 工业设计方向汇总

| 平台 | 对"数据外传"的防护模式 | 关键机制 |
|------|----------------------|---------|
| Anthropic | 工具风险分级 + 沙箱 + 权限模式 | 权限档（default/acceptEdits/plan/bypass） |
| OpenAI | 工具审批默认开启 + 输入/输出护栏 | Guardrails + HITL + Lockdown Mode |
| AWS | 可插拔 Guardrails + 策略授权 | Denied topics + PII 阻断 + Cedar 策略 |
| Google | 网关层 DLP 独立于意图 | Agent Gateway ISV + DLP 检测 |
| Microsoft | Purview DLP 直接管 Agent 端点 | 输出侧 DLP + ADR 审批原则 |
| 框架层 | 工具调用边界挂闸 | Hooks + Interrupt + RBAC |

## 二、学术方向

### 2.1 LLM Agent 安全综述

- **《SoK: The Attack Surface of Agentic AI》** ([ar5iv](https://ar5iv.labs.arxiv.org/html/2603.22928))：把 LLM 视为**不可信规划器（untrusted planner）**，每次动作提议都应被显式机制仲裁
- **《Agent Security Bench (ASB)》** (ICLR 2025, [ICLR](https://proceedings.iclr.cc/paper_files/paper/2025/hash/5750f91d8fb9d5c02bd8ad2c3b44456b-Abstract-Conference.html))：攻击→防御→再攻击的评估协议
- **《A Comprehensive Survey in LLM(-Agent) Full Stack Safety》** ([arXiv:2504.15585](https://arxiv.org/html/2504.15585v3))：数据层/训练层/部署层全栈划分
- **《Navigating the Risks: Security, Privacy, and Ethics Threats in LLM-Based Agents》** ([arXiv:2411.09523](https://arxiv.org/abs/2411.09523))：Agent 安全/隐私/伦理威胁盘点

**关键共识**：防线分为**输入端（提示注入防御）— 决策端（工具/动作权限仲裁）— 输出端（泄露监测）**三环；"代理过度授权（excessive agency）"已是公认头号结构性风险。

### 2.2 间接提示注入与数据外传攻击

- **《InjecAgent: Benchmarking Indirect Prompt Injections》** ([arXiv:2403.02691](https://arxiv.org/abs/2403.02691))：首个系统性基准，GPT-4 在危险工具场景 ISR 高达 24%。**仅靠提示语不可靠，必须依赖工具层强制约束**
- **《AgentPoison: Red-teaming LLM Agents via Poisoning Memory》** ([arXiv:2407.12784](https://ar5iv.labs.arxiv.org/html/2407.12784))：污染知识库/记忆诱导 Agent 执行危险动作，直接威胁"读取类操作"安全
- **《Silent Egress: When Implicit Prompt Injection Makes LLM Agents Leak Without a Trace》** ([ADS](https://ui.adsabs.harvard.edu/abs/2026arXiv260222450L/abstract))：**明确以"egress"为攻击目标命名**——隐式注入让 Agent 无痕外传数据。与本盲区对口度最高的论文

### 2.3 Confused Deputy 问题

- **《ConfusedPilot: Confused Deputy Risks in RAG-based LLMs》** ([arXiv:2408.04870](http://export.arxiv.org/pdf/2408.04870))：首个把 confused deputy 概念系统迁移到 RAG LLM 的论文——检索增强系统中的注入可使模型泄露未授权内容
- **《Securing LLM Applications: Addressing the Confused Deputy Problem》**（[Globant](https://stayrelevant.globant.com/en/technology/data-ai/securing-llm-applications-addressing-confused-deputy-problem/)）：工业界指出 confused deputy 是 LLM 工具集成的主要漏洞类别

**关键结论**：**权限不应由"意图文本"决定，而应由"请求来源的可信度 + 操作本身的最低权限"决定**；读取与外发应分离授权。

### 2.4 工具调用安全：最小权限 + 能力隔离

- **《MiniScope: A Least Privilege Framework for Tool Calling Agents》** ([Berkeley](https://sky.cs.berkeley.edu/project/miniscope/))：为每个工具调用做最小权限授权，动作与权限分开建模——最贴近 Voyage 的 query/execute 分类的学术原型
- **《ToolGuardian: Declarative Security for AI Agent-Tool Interactions》** ([arXiv](https://arxiv-org.ezproxy.obspm.fr/html/2607.21835v1))：声明式策略文件约束 Agent-工具交互
- **《Sandlock: Confining AI Agent Code》** ([Semantic Scholar](https://www.semanticscholar.org/paper/Sandlock%3A-Confining-AI-Agent-Code-with-Unprivileged-Wang-Zheng/37b4c1869b865ab54a6dfa98d8916775fa1551d9))：OS 层能力隔离
- **mcpguard-dynamic** ([Facebook/Meta](https://github.com/facebook/mcpguard-dynamic))：eBPF 内核级沙箱，对 MCP 工具调用做内核级强制隔离

### 2.5 有害意图识别与危险动作检测

- **《Intent-Governed Tool Authorization for AI Agents》** ([arXiv](https://arxiv-org.ezproxy.obspm.fr/html/2606.22916v1))：意图驱动的工具授权——与 Voyage 方案对齐度最高，但也暴露二元/意图分类的固有难题：**"读取+发送"组合意图容易被误判为只读**
- **《Monitoring LLM Agents for Sequentially Contextual Harm》** (ICLRW 2025, [链接](https://mlanthology.org/iclrw/2025/yuehhan2025iclrw-monitoring/))：危险不是单步动作而是**跨步骤累积**——单看"读文件"无害，加一步"发出去"才有害。**对"query 免审批"盲区是精准打击**
- **agent-action-guard** ([PyPI](https://pypi.org/project/agent-action-guard/1.0.5/))：Agent 动作实时分类为 safe/harmful/unethical 的开源实现

### 2.6 Guardrails 安全护栏

- **NeMo Guardrails** ([NVIDIA](https://docs.nvidia.com/nemo/guardrails/latest/resources/research.md))：最早的工程化护栏框架，动作护栏可拦截危险工具调用
- **《AGrail: A Lifelong Agent Guardrail》** (ACL 2025, [ACL Anthology](https://aclanthology.org/2025.acl-long.399/))：终身学习式护栏
- **《GuardAgent: Safeguard LLM Agents by a Guard Agent》** ([arXiv:2406.09187](https://arxiv-org.ezproxy.obspm.fr/html/2406.09187v3))：**双层代理架构**——主代理决策、守卫代理审核
- **《Symbolic Guardrails for Domain-Specific Agents》** ([arXiv](https://arxiv-org.ezproxy.obspm.fr/html/2604.15579v1))：对可枚举的敏感动作，**确定性规则（符号护栏）比概率判断可靠**

### 2.7 检索/读取类操作安全

- **《Authorization-First Retrieval: Enforcing Least Privilege in Multi-Agent RAG》** (TrustNLP, [ACL Anthology](https://aclanthology.org/2026.trustnlp-main.15/))：**先鉴权后检索**——把文档级权限应用到检索结果过滤，与"读取也需分级授权"方向一致
- **《VectorSmuggle: Steganographic Exfiltration in Embedding Stores》** ([HuggingFace](https://huggingface.co/papers/2605.13764))：连嵌入向量库都可能成为隐写外传通道

### ▶ 学术共识与未解决问题

**共识**：
1. **"读取"不能免审**——ConfusedPilot、Authorization-First Retrieval 都证明读取本身就是泄露通道
2. **危险是"跨步骤/组合"属性**——单步 query 分类必然有盲区（Monitoring LLM Agents、Silent Egress）
3. **敏感动作要用确定性规则兜底**——符号护栏、OWASP LLM06 都指向规则而非概率判定
4. **最小权限要落到"调用级"**——MiniScope、ToolGuardian 把每次工具调用与权限分离建模

**未解决问题**：
- "数据外传/egress 作为独立风险维度"的**正式分类法尚不存在**——主流的 OWASP LLM Top 10 仍把这类风险归在"提示注入""过度代理"之下。Voyage 的盲区正好处于研究前沿与分类法空白之间，可视为潜在可发表方向

## 三、竞品方向

### 3.1 PagerDuty AIOps

- **产品**：PagerDuty Advance（AIOps 事件响应 + 自动化修复）
- **安全模型**：**人工确认门 + 可配置自动化**——PagerDuty 的自动化操作（auto-remediation）默认需人工确认（acknowledge-before-act），高危动作强制暂停等待 SRE 批准。社区实践 [How I Built an AI Agent That Handles On-Call Incidents and Pauses for Human Approval](https://dev.to/krishna_kittu_1d2837d30bb/how-i-built-an-ai-agent-that-handles-on-call-incidents-and-pauses-for-human-approval-before-53a3) 展示了这一模式
- **数据外传防护**：无公开的专用 DLP/egress 文档

### 3.2 Datadog Bits AI

- **产品**：[Bits AI](https://docs.datadoghq.com/bits_ai/bits_security_analyst/)——自然语言查询 + 安全分析
- **安全模型**：Bits 主要定位为查询/分析助手（只读为主），操作类能力（如通过 Custom Agents 触发自动化）需通过平台既定权限控制。文档 [Custom Agents](https://docs.datadoghq.com/incident_response/work_management/ai/custom_agents/) 支持自定义 agent 行为
- **数据外传防护**：无公开专用 DLP 文档

### 3.3 AWS（Amazon Q Developer + Bedrock Agents）

- **产品**：Amazon Q Developer（之前是 AWS Chatbot）可调用 [Bedrock Agents](https://docs.aws.amazon.com/chatbot/latest/adminguide/connect-bedrock-agents.html) 在聊天中执行运维操作
- **安全模型**：IAM 身份策略 + Bedrock Guardrails（前文已述）+ HITL 确认模式
- **数据外传防护**：Bedrock Sensitive Information Filters（PII block/redact）

### 3.4 Microsoft（Copilot for Azure / Azure Monitor）

- **产品**：Copilot for Azure（Azure 门户中的 AI 助手）、Azure Monitor 智能运维
- **安全模型**：Azure AI Foundry Guardrails + Purview DLP（前文已述）+ [Copilot Governance Maturity Model](https://www.m365.fm/blog/copilot-governance-maturity-model-framework-challenges-and-practical-implementation/)
- **数据外传防护**：Purview DLP 直接监控 Copilot 输入输出；[Purview DLP 保护 Copilot 免受数据外泄](https://microsoft.github.io/mwkorea/copilot/PurviewDLPExternalWebSearchCopilot/)

### 3.5 Google Cloud（Gemini Cloud Assist）

- **产品**：[Gemini Cloud Assist](https://www.megazonesoft.com/250623-geminiassist/)——Google Cloud 中的 AI 运维助手
- **安全模型**：Google ADK Safety 框架（[docs](https://raw.githubusercontent.com/google/adk-docs/main/docs/safety/index.md)）+ Agent Gateway 网关层安全
- **数据外传防护**：Google 的 Agent Gateway ISV 生态让第三方 DLP 在网关层拦截 agent 对外流量

### 3.6 Splunk AI Assistant

## 四、安全标准与框架方向

### 4.1 OWASP LLM Top 10（2025）

- **LLM06: Excessive Agency**（[OWASP 官方](https://owasp.org/www-project-top-10-for-large-language-model-applications/2_0_vulns/LLM06_ExcessiveAgency.html)）："过度代理/权限过大"——agent 拥有超出必要权限的操作范围。**推荐控制**：限制工具权限、要求人工审批高危动作、**对敏感操作（含数据读取）按最小权限原则授权**
- **LLM02: Sensitive Information Disclosure**：敏感信息泄露。**推荐控制**：输出过滤、数据分类、最小化输出范围
- **Voyage 盲区对应条目**：**LLM06 Excessive Agency**——query 路径拥有"读取+外发"的权限，却没有分级授权。这是"过度代理"的典型表现

### 4.2 OWASP Top 10 for Agentic Applications（2025 年 12 月新增）

- **官方发布**：[OWASP GenAI Security Project Releases Top 10 for Agentic AI Security](https://genai.owasp.org/2025/12/09/owasp-genai-security-project-releases-top-10-risks-and-mitigations-for-agentic-ai-security/)
- 涵盖 agent 特有的风险：**APP-02: Insecure Agent-to-Agent Communication**、**APP-04: Excessive Agency**、**APP-05: Insecure Input/Output Handling**、**APP-08: Data Leakage via Agent Actions**——**"通过 agent 动作的数据泄露"被列为独立条目**
- 来源：[OWASP 官方博客](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/)、[Promptfoo 集成](https://www.promptfoo.dev/docs/red-team/owasp-agentic-ai/)、[TechRepublic 报道](https://www.techrepublic.com/article/news-owasp-ai-agent-risk-list/)
- **Voyage 盲区对应条目**：**APP-08: Data Leakage via Agent Actions**——"读文件+外发"正是 agent 动作导致的数据泄露

### 4.3 MITRE ATLAS

- **AI agent 攻击技术**：MITRE ATLAS 已涵盖 agentic AI 相关 TTP（[NHIM 分析](https://nhimg.org/community/agentic-ai-and-nhis/ai-agent-attack-techniques-in-atlas-what-changes-for-iam-teams/)），包括 `llm-tool-use-exfil`（agentic AI 工具滥用经提示注入外传数据）
- **数据外传 TTP**：T1030 Data Transfer Size Limits 等，但 ATLAS 对 agent 数据外传的系统化分类仍在完善中

### 4.4 NIST AI RMF / AI 600-1

- **NIST AI RMF**：AI 风险管理框架，覆盖治理、映射、度量、管理四个功能
- **NIST AI 600-1**：AI 安全治理指南。开源社区已有 [agentic-security 覆盖度映射](https://github.com/Clear-Capabilities/agentic-security/blob/main/docs/compliance/nist-ai-600-1-coverage.md)，将 agent 安全控制映射到 NIST 框架
- **Berkeley Agentic AI Profile**（[Stanford Law](https://law.stanford.edu/2026/03/07/kill-switches-dont-work-if-the-agent-writes-the-policy-the-berkeley-agentic-ai-profile-through-the-ailccp-lens/)）：UC Berkeley 发布的 55 页 Agentic AI 风险管理标准 Profile，核心发现："Kill switches don't work if the agent writes the policy"——**Agent 不能拥有改写自身安全策略的权限**

### 4.5 人类审批门（Human-in-the-loop）的标准定位

- **NIST 相关**：AI 600-1 和 NIST IR 推荐对高风险 AI 动作实施 human-in-the-loop 或 human-over-the-loop
- **Pindrop 分析**（[NIST reaction: AI Agents Need Identity and Human Approval](https://www.pindrop.com/article/nist-reaction-ai-agents-need-identity-and-human-approval-needs-verification/)）：NIST 反应表明 AI agent 需要身份认证和人类批准的验证机制
- **行业共识**：HITL 对"写操作"（execute）已普遍接受，但**对"读+外传"类操作是否需要 HITL 尚无行业标准**

### ▶ 标准对照结论

| 标准 | 对应条目 | Voyage 的盲区性质 |
|------|---------|-----------------|
| OWASP LLM Top 10 (2025) | **LLM06 Excessive Agency** | query 路径拥有"读取+外发"但无分级授权，是过度代理 |
| OWASP Agentic Top 10 (2025) | **APP-08 Data Leakage via Agent Actions** | agent 动作导致数据泄露 |
| MITRE ATLAS | `llm-tool-use-exfil` | 工具滥用经提示注入外传 |
| NIST AI RMF | 映射到 MAP/GOVERN 功能 | 风险治理缺失——"数据外传"未被识别为 AI 操作风险 |

**业界推荐的标准控制清单**：
1. **最小权限工具授权**（OWASP LLM06）：任何工具调用（含读）按需授权，不默认放行
2. **输出侧 DLP 过滤**（OWASP LLM02、APP-08）：无论意图分类结果如何，出站内容过敏感数据过滤
3. **人类审批高危动作**（NIST AI RMF）：对读+外发类操作应走 HITL
4. **分离"读取"与"外发"授权**：不把"读文件"和"发文件"作为同一授权级别
5. **Agent 不可改写自身安全策略**（Berkeley Profile）：agent 不能拥有改写安全策略的权限

## 五、综合分析与对 Voyage 的启示

### 核心发现

**1. 业界普遍不把"读取"当作天然安全。** 从 Anthropic 到 OpenAI 到 AWS 到 Google 到 Microsoft，**共识是"数据出站必须独立于意图分类"**。Voyage 的"query 免审批"设计在业界是孤例，已被证明有盲区。

**2. 学术界正在收敛到"数据外传(egress)作为独立维度"**——《Silent Egress》明确以 egress 为攻击目标命名，OWASP Agentic Top 10 新增 APP-08 Data Leakage via Agent Actions，MITRE ATLAS 已覆盖 `llm-tool-use-exfil`。但**正式分类法尚不存在**，Voyage 处于前沿与空白之间。

**3. 竞品都没有完美的"数据外传防护"解决方案。** 多数平台（PagerDuty、Datadog、Splunk）没有公开的专用 DLP/egress 控制。AWS Bedrock 和 Microsoft Purview 是最接近完整方案的，但它们依赖的是**独立于意图层的输出侧 DLP 网关**，而非意图分类的改进。

### 对 Voyage 方案设计的 5 条启示

| # | 启示 | 来源 | 对应方案 |
|---|------|------|---------|
| 1 | **审批绑定"工具"而非"意图标签"** | OpenAI Safety Guide、Microsoft ADR 0006 | 改分类器引入 egress 轴，或直接按工具 profile 授权 |
| 2 | **数据出站设独立 DLP 闸门** | Google Agent Gateway、Purview DLP、Bedrock Guardrails | 在编排层或输出层加 egress 检测，不依赖意图分类 |
| 3 | **"只读"做成执行器硬约束** | Anthopic Sandboxing、django-mcp-sql | 读文件工具在实现层强制只读+路径白名单，外发必须走审批通道 |
| 4 | **护栏分层且 deny 优先** | Anthropic hooks issue #39344、Amazon Q 默认过宽投诉 | deny 优先于 ask/allow；未显式允许即拒绝 |
| 5 | **评估基准可量化盲区** | InjecAgent ISR、ASB 攻防协议 | 用 HR-031 和更多 egress 样本在高危集持续回归，量化当前盲区 |

### 本质结论

**Voyage 的盲区不是"发现了一个 bug"，而是"站在了行业共识的反面"**——行业已从"按意图是否变更做审批"演进到"按工具是否能造成数据出站做审批"，而 Voyage 的 DDD 模型仍停留在意图二元分类。这不是实现漂移，而是初始建模时选错了分类轴。
