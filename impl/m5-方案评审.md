## 2. 设计决策（含依据与理由）

### 2.1 编排层 IntegrationService（统一入口，DoD-B「统一入口」服务端强制）

- **入口唯一性**：UI 全部动作经 `integration.handle(intent)` 进入；服务端按 DDD §6 五步判定点**顺序串联**，不信任前端传入的任何「已判定/已授权」标志（前端隐藏不隔离——UI 隐藏不算）。
- **五步判定点顺序**（DDD §6，服务端强制）：
  1. **意图层**（conv）：动词重分类 → 意图类型定稿（执行类/查询类区分）。
  2. **拆解前**（trust.evaluate）：高危判定（滑动窗口聚合/跨桶/跨资产）→ 高危？→ 须审批。
  3. **执行前**（exec gateway）：`白名单 ∩ 矩阵` + 参数 schema + Grant 校验 + 资产退役 + 聚合升级标志（M4 已实现判定点 3，此处串联复用）。
  4. **审批链**（trust）：WebAuthn 唯一通道、双人、不可自批、超时同事务、幂等（M3 已实现 resolveApproval；本层按 Outbox 语义接线驱动执行启动）。
  5. **审计**（audit）：五元组先行写入，写失败即回滚（写操作 fail-closed）。
- **关键设计决定**：本层不重复实现各判定点内部逻辑，而是**端口编排 + 断言接线**——依赖 injected 的 convPort/evaluatePort/execPort/trustPort/auditPort，把各 BC 领域服务串成一条服务端强制管线，并对每步返回做结构校验 + 失败语义归一（OK/REJECTED/ERROR，DDD §4）。
- **六元组审计先行**：`handle` 在「触发执行」前必先 `audit.write` 成功；failure → ERROR，不进入执行链（INV-U1）。

### 2.2 Outbox 事务边界（RQ-623 编排层落地，DDD §7 机制 1/5/6）

- **背景**：M3 领域层已声明「批准即签发 Grant，'同事务'事务边界 Outbox 归 M5 编排层」；M4 exec 侧已实现幂等订阅（eventId 去重）。M5 编排层补齐**跨 BC 最终一致性**结构。
- **Outbox 消息聚合 `OutboxMessage`**（本层新增）：审批决定/Grant 签发/审计写入在**单一编排事务上下文**内：
  ```
  enqueue({ localTx, event }) → message { id, event, status: pending, attemptCount: 0, nextAttemptAt, createdAt }
  ```
  本地事务提交时消息入队；提交失败 → 整链 fail-closed，不留半程副作用（RQ-831）。
- **消费语义**（DDD §7 契约，可测）：
  - **消息 ID 幂等去重（消费端）**：同 messageId 不得重复驱动副作用 —— 复用 M4 `_seenEventIds` 思路，本层以 `consumedMessageIds` 去重。
  - **失败指数退避重试**：`attemptCount` 递增，`nextAttemptAt = now + BASE * 2^attemptCount`（BASE 目标值，实测校准）。
  - **超限转死信 + 告警（INV-N2 关键告警不静默）**：attemptCount ≥ MAX_RETRIES → status=dead；必须触发 `alertPort.notify(消息死信)`，**静默转死信 = 违规**。
- **竞态裁决（DDD §7 机制 5）**：审批超时与聚合升级同时触发 → 「更保守者胜」（任一拒绝/升级即拒绝执行）；同一事务内固定序（先聚合升级判定、后超时判定）串行。
- **单写者时序（DDD §7 机制 6）**：审批单/Grant/审计事件状态迁移由**唯一权威节点串行**（本层 Outbox 消费端 enforced serial），避免时钟偏差 → 超时判定不一致。

### 2.3 审计聚合 AppendOnlyAuditChain（RQ-831 / INV-U3）

- **背景**：审计 BC 在 `impl` 下尚无实现（M1~M4 均有 auditPort stub）。M5 补齐审计聚合本体。
- **五元组**（DDD §3 schema）：`{ who, when, from, action{intent,capability,target,params-schema-ok}, result, links{approvalId?,grantId?,aggregationEscalation?}, integrity{chainHash,seq} }`。
- **append-only 哈希链**（INV-U3）：每条审计预先算哈希并入链（prevHash 引用），链尾哈希（`tailHash`）可由任意后续 entry 校验。append-only —— 不允许覆写/删除（去除篡改面）。
- **审计先行 fail-closed**（INV-U1）：写入失败（存储端口异常）→ 写操作回滚（写面导出，不执行）。
- **降级态（DDD §7 机制 2）**：审计存储不可用 → 写面只读 + 审批；审批走落盘缓冲（独立持久介质）重试，恢复后补齐入哈希链（本里程碑实现缓冲队列 + 哈希链重建契约，真实介质归适配器）。

### 2.4 真实适配器（本里程碑契约端口 + stub，M6 接真实）

| 端口 | 方法 | 本里程碑 |
|------|------|---------|
| `convPort` | `interpret(intent)` → {intentType, confidence, subject} | stub（策略：<0.8 执行类降级确认） |
| `evaluatePort` | `evaluate(subject, intent)` → {escalated, ...} | 注入 M3 语义（契约桩） |
| `execPort` | `start / complete / fail` | 注入 M4 ExecutionService（契约复用） |
| `trustPort` | `handleExecIntent / resolveApproval / checkGrant` | 注入 M3 ApprovalFlowService |
| `auditPort` | `write(五元组)` | 注入本层 AppendOnlyAuditChain |
| `keyVaultPort` | `ref` | 契约端口（M6 SSH 凭据保险库） |
| `notifyPort` | `notify(event)` | 契约端口（INV-N2 死信/审批提醒） |
| `timeSource` | `() => Date` | 可注入（超时/退避判定一致性） |

- **关键设计决定**：适配器以「契约端口 + stub」落地，测试保证替换条件（对齐 M4 同策略）；真实 mTLS/WebAuthn 设备认证、SSH 被管机执行、审计 ≥180 天介质、角色-资产真实仓储全部归 **M6 内测上线 / 真实选型**，不在 M5 象征性占用硬件。

## 4. 测试规划（五类）

- **happy**：H1 意图→查询类直接应答（无执行）；H2 高危→审批→批准→Grant→Outbox→exec 启动全链路；H3 非高危自动 Grant→exec 启动；H4 审计五元组写入含 chainHash 入链；H5 Outbox 消息正常消费驱动执行。
- **error**：E1 矩阵 ❌/非白名单/参数 schema → REJECTED 原因码；E2 Grant 无效/过期/吊销拒绝；E3 审计写入失败 → ERROR fail-closed 不执行；E4 前端伪「已授权」标志 → 服务端重判拒绝（不可信前端）。
- **edge**：G1 聚合升级→挂起转审批→恢复；G2 审批超时 vs 聚合升级同时触发 → 更保守者胜；G3 Outbox 退避（首败→nextAttemptAt 递增）；G4 死信重试上限→dead + 告警触发。
- **adversarial**：A1 Outbox 同 messageId 重放不重复副作用；A2 审计链篡改中间 entry → tailHash 校验失败；A3 审计 append 试图覆写 → 拒绝；A4 输入超长/原型链保留键拒绝。
- **fault-tolerance**：F1 审计存储端口异常 → 降级态（写面只读+审批，缓冲队列）；F2 时间倒退 → 拒绝；F3 端口返回畸形 → 结构校验 fail-fast；F4 告警端口本身失败 → 死信不静默（仍记录）。
