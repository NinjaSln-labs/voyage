| 不变量 | 实现 | 结论 |
|--------|------|------|
| INV-E1：非 read 类意图先过信任预检再拆解 | `decompose()` 无条件接受任何 intent，**没有前置信任预检** | **D2（P2）** 偏差 |
| 能力白名单校验 | ✅ DAGNode 构造时校验 `C2_CAPABILITIES` | ✅ |

### 2.4 发现

**D1（P2）**：DDD 设计 §5 定义 `Task{id, dag[], status}`，实现用了 `nodes[]` 替代 `dag[]`。虽然语义上 `nodes` 更清晰（DAGNode 的集合），但设计文档未同步更新，存在术语偏差。

**建议**：更新 `DDD设计.md` §5 中 `Task` 定义为 `Task{id, nodes[], status}`（无环），或在代码注释中说明别名。

**D2（P2）**：`INV-E1` 要求「非 read 类意图（write/egress/authorize）先过信任预检（角色能力✓/Grant✓/资产未退役✓/高危面匹配✓）再拆解」。当前 `decompose()` 无条件接收任何 intent，不检查意图是否已通过信任预检。这意味着 write/egress 类意图可以在未经信任预检的情况下被拆解，虽然编排层（M5）在消费事件时仍会执行信任预检再执行，但**领域服务本身没有防御性校验**。

**举例**：`decompose({actionClass: 'write', capability: 'restart', target: 'jd-light', ...})` 直接拆解为 1 个节点，但 `restart` 是 write 类能力，按 INV-E1 应先过信任预检。当前 decompose 没有拒绝未经信任预检的意图。

**影响**：如果该 decompose 被直接调用（绕过编排层），可能产生未经验证的子任务节点。M5 编排层在消费事件后会做信任预检，所以安全链完整，但领域服务有防御性缺口。

**D3（P3）**：egress 拆解路径生成 `clean` 能力节点作为 prepare 步骤。`clean` 是 write 类能力，需要自己的 Grant 和审批。当前 `decompose()` 直接生成 clean 节点，没有走任何授权检查。同上，安全链依赖编排层补全，但领域服务缺少防御性约束。

**D4（P3）**：`Task` 的 `_updateStatus` 是私有方法，外部无法直接更新任务状态。`TaskService.updateNodeStatus` 只做校验返回 `{ok, nextStatus}`，不真正更新状态。这一设计**合理**（状态由编排层控制），但缺少公开的 `Task.start()`/`Task.complete()`/`Task.fail()` 方法，与 M4 `Job` 的使用模式不一致。

**建议**：可以考虑在 `Task` 上增加公开状态变更方法（`start/complete/fail`），保持与 M4 `Job` 相同的领域模式。当前模式**不阻断功能**，但增加了编排层的复杂度。
